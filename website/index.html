// three ideas

What the language is built around

Metaxu compiles to native code through LLVM. Three decisions shape everything else.

effects

Effects are the machine model

Threads, mutexes, streams, and GPU kernel launches are all algebraic effects with handlers, backed by real delimited continuations (native try/catch, streams, generators).

A handler can virtualize any of them, so the same program runs on a test double, a thread pool, or a GPU.

modes

Modes instead of lifetimes

Memory safety comes from a small set of inferred modal axes, checked by a borrow checker that propagates properties instead of asking you to annotate them.

Thread-safety is inferred, never declared: crossing a value into another thread marks it, and unsynchronized writes to crossed values are caught: statically where provable, dynamically otherwise, with the same error wording either way.

reference

The interpreter is the spec

Every backend is differentially tested against a strict reference interpreter, byte for byte: output, error messages, float formatting.

A whole class of silently-wrong-code bugs is found by these tests instead of by users.

# Re-emit only elements with pred(x) true.
fn filter(producer, pred) -> fn() -> Unit {
    fn() {
        handle Emit with {
            emit(x) -> {
                if pred(x) { perform Emit.emit(x) } else { () };
                resume(())
            }
        } in {
            producer();
            ()
        }
    }
}
matmul_kernel.mxa tile-level GPU kernel, no raw pointers
// A GPU kernel: one instance per output tile, masked edges, no raw pointers.
from std.gpu import Gpu, run_grid;

fn mm_kernel(pid: int, a: Vec, b: Vec, c: Vec) -> () {
    let ti = pid / 16;  let tj = pid % 16;
    let mut k = 0;
    let mut r = Tile.filled(8, 8, 0);
    while k < 16 {
        let ta = Tile.load_rows(a, (ti * 8) * 128 + k * 8, 128, 8, 8, 0);
        let tb = Tile.load_rows(b, (k * 8) * 128 + tj * 8, 128, 8, 8, 0);
        r = Tile.add(r, Tile.dot(ta, tb));
        k = k + 1
    };
    Tile.store_rows(c, (ti * 8) * 128 + tj * 8, 128, r);
    ()
}
// perform Gpu.launch(256, fn(pid: int) -> mm_kernel(pid, a, b, c));

Performance against C

Every benchmark asserts output equality between the Metaxu program and its hand-written C twin before any timing runs. Same clang, same -O2, -falign-functions=64 everywhere, alternating run order, medians. Alignment is pinned because unaligned microbenchmarks mostly measure code placement.

orbit at 0.99x: value semantics at C speed

The Metaxu version rebuilds an immutable 4-field struct every step and costs the same as C mutating doubles in place. SROA and mem2reg remove the struct entirely at -O2.

nsieve’s 9% is the bounds-check price

It sat at ~1.4x when every v[i] was an opaque runtime call; inline fast paths closed most of that. The rest is the checked-indexing price: out-of-bounds is a runtime error, and data races on crossed vecs are caught. Bounds-checked Vec loops generally run ~1.3–1.7x C.

effects have a measured price

A handler crossing costs ~280 ns; each pipeline element crosses filter, map and sum. Threads reach parity once the work amortizes ~2.5 ms of flat spawn cost: four threads process 40M elements about 3.4x faster than the serial pass in the same binary.

// gpu tiles, in progress

Triton-class tile kernels, Apple-first

Kernels are programs over Tile[T, R, C] values with shapes static in the type, not per-thread code. The tile semantics, shape checker and (later) layout inference are target-neutral; backends are thin text emitters. Metal Shading Language first, bound into MLX; textual TritonGPU MLIR later for NVIDIA/AMD.

Stage 0 landed
The portable core, no GPU anywhere. Tile[T,R,C] with compile-time shape errors, deterministic interpreter semantics as the reference, a native tile runtime, and a differential gate: 19 tests, byte-identical output on both engines, including catchable bounds raises.
Stage 1a–1c landed
The kernel seam. Strict and masked buffer↔tile IO (Tile.load_or, Tile.store_clipped); Gpu.launch as pure library: effect Gpu { launch(n, f) = run_grid(n, f) }, default handler = the sequential CPU reference, zero compiler changes; and the first MSL emitter with a self-checking Mac harness (mx.fast.metal_kernel, interpreter-computed expected values baked in).
Stage 1d landed
f32 tiles → float Metal kernels. f32 is a tile element kind (language scalars stay f64): elements live as f32-representable doubles and every op rounds once, so results are bit-identical across the interpreter, native, and the C++-shimmed MSL lowering, pinned against an independently computed f32 matmul.
Stage 1e landed
The Metal runtime handler. Install run_metal over Gpu.launch and the same kernel dispatches through mx.fast.metal_kernel on Apple silicon, or through a bit-exact shim engine elsewhere; the shim is how the handler is tested with no GPU in the container. Anything outside the contract is an error; there is no silent CPU fallback.
Stage 1, open next
f16 by the same recipe; the gpu effect class.
Stages 2–3 ahead
Inferred layouts with costed convert_layout, simdgroup_matrix dot, threadgroup-memory tiling; then explicit layout annotations, an autotuner, and a TritonGPU-text emitter for NVIDIA/AMD.

The 4x tile overhead is incidental, not intrinsic

Measured 2026-08-26: the tiled 128³ matmul running through Gpu.launch on the CPU reference costs ~4x plain C loops. Every tile op is an opaque runtime call that allocates a fresh block; the reference lowering is functional by design, and stays unoptimized on purpose.

Lowering the same kernel through the MSL emitter (tiles as stack arrays, zero allocation, ops inlined) and racing it on the same workload gives:

functional CPU reference  ~4x C   ·   MSL-style lowering of the same kernel  ~0.9–1.0x C

The tile model itself costs nothing; the reference lowering does. That also bounds what a future fused CPU lowering can recover. The number is tracked in benchmarks/diagnostics so it stays visible.

// why “metaxu”

Why the name

The name comes from Simone Weil’s metaxu: the wall between two prison cells separates the prisoners, and is also what they tap messages through.

Metaxu aims to be that kind of intermediary: a bridge between high-level abstractions and low-level performance. The goal is systems programming that is safe and fast without a steep annotation burden.

The compiler itself is meant to be readable: a Python front end with text-emitting backends, built so that anyone can learn how compilers are made.
